3b. Curvas de aprendizaje — Train RMSE vs Val RMSE por época#

Las curvas de aprendizaje muestran la evolución del RMSE en entrenamiento y validación a lo largo de las épocas para la arquitectura seleccionada por el grid search (lag=14d, fold=0). Permiten verificar:

  • Sobreajuste (overfitting): val_rmse sube mientras train_rmse baja

  • Subajuste (underfitting): ambas curvas convergen a un RMSE alto

  • Buen ajuste: ambas curvas descienden y se estabilizan con gap pequeño

Fuente: grid_results_checkpoint.pkl — curvas guardadas durante el grid search para la configuración ganadora de cada modelo.

# ── Extraer curva de la mejor arquitectura por modelo ─────────────────────────
# La mejor arquitectura = la misma que seleccionó best_configs en el training
# (menor val_rmse con gap_ratio < 0.15). La buscamos directamente en el checkpoint.

def get_best_curve(checkpoint, mtype):
    """Devuelve (train_curve, val_curve, meta) de la mejor config del modelo."""
    v = checkpoint[mtype]
    # Normalizar a lista de dicts
    if isinstance(v, dict):
        records = v.get('results', [])
    else:
        # legacy DataFrame
        records = v.to_dict('records')

    if not records:
        return None, None, None

    # Filtrar candidatos con gap_ratio < 0.15, ordenar por best_val_rmse
    candidates = [r for r in records
                  if r.get('gap_ratio', 999) < 0.15
                  and 'train_curve' in r
                  and 'val_curve' in r]
    if not candidates:
        candidates = [r for r in records
                      if 'train_curve' in r and 'val_curve' in r]
    if not candidates:
        return None, None, None

    best = min(candidates, key=lambda r: r.get('best_val_rmse', 999))
    return (
        best['train_curve'],
        best['val_curve'],
        {
            'arquitectura':  best.get('arquitectura'),
            'dropout_mask':  best.get('dropout_mask'),
            'best_val_rmse': best.get('best_val_rmse'),
            'gap_ratio':     best.get('gap_ratio'),
            'epochs_run':    best.get('epochs_run'),
        }
    )

learning_curves = {}
for mtype in MTYPES:
    if mtype not in checkpoint:
        print(f'⚠️  {mtype} no encontrado en checkpoint — omitiendo')
        continue
    tr, val, meta = get_best_curve(checkpoint, mtype)
    if tr is None:
        print(f'⚠️  {mtype}: curvas no disponibles (checkpoint legacy sin train_curve)')
        continue
    learning_curves[mtype] = {'train': tr, 'val': val, 'meta': meta}
    print(f'✅ {mtype}: arch={meta["arquitectura"]} | '
          f'val_rmse={meta["best_val_rmse"]:.5f} | '
          f'gap_ratio={meta["gap_ratio"]:.3f} | '
          f'épocas={meta["epochs_run"]}')

if not learning_curves:
    print('\n⚠️  No hay curvas de aprendizaje disponibles.')
    print('   Esto ocurre cuando el checkpoint fue generado sin guardar train_curve/val_curve.')
    print('   Solución: re-correr la sección 7 del notebook 3_model_training.ipynb.')

MLP — Curvas de aprendizaje#

Nota metodológica: Las curvas del MLP fueron generadas desde el grid_results_checkpoint.pkl. El RMSE está en espacio estandarizado (antes de inverse_transform), por lo que los valores absolutos difieren de las métricas de evaluación final — pero la forma de la curva (convergencia, estabilidad, gap train/val) es equivalente e informativa para el diagnóstico de sobreajuste.

Observaciones:

  • Con lag corto (7d) el MLP converge sin sobreajuste — la train loss desciende sostenidamente y el Val R² se estabiliza por encima de 0.7.

  • Con lags más largos (21d, 28d) aparece sobreajuste moderado: el modelo memoriza patrones del training que no generalizan, consistente con el degradamiento de RMSE observado en lag=28d en la evaluación final.

  • El early stopping actúa correctamente en todos los casos. La curva no diverge, simplemente el gap train/val se amplía.

Sobre la interpretación del gap train/val

En las arquitecturas RNN y LSTM, el Train RMSE aparece consistentemente por encima del Val RMSE. Esto no es un artefacto ni un error de implementación: es el comportamiento esperado cuando se usa Dropout. Durante el entrenamiento, el Dropout desactiva aleatoriamente una fracción de las neuronas en cada paso, lo que degrada intencionalmente la capacidad del modelo y eleva su error sobre los datos de entrenamiento. En validación e inferencia, el Dropout se desactiva por completo, permitiendo que todas las neuronas contribuyan — de ahí que el modelo rinda mejor en validación que en entrenamiento.

El gap_ratio elevado que se observa en estas curvas no indica sobreajuste; indica que el Dropout está funcionando como regularizador. El sobreajuste real se manifestaría en la dirección opuesta: val RMSE subiendo mientras train RMSE baja. Ese patrón no aparece en ninguno de los modelos seleccionados.

Por otro lado, los gap_ratio elevados observados en lag=28 son consistentes entre los tres modelos y no responden a la arquitectura sino al horizonte de memoria: una ventana de 28 días abarca regímenes de volatilidad heterogéneos en BTC que el modelo no puede reconciliar dentro de un mismo fold. Ese lag fue descartado durante la selección y no forma parte del modelo desplegado.

# ── Función auxiliar: gráfica de curvas para un (mtype, lag, fold) ───────────
def plot_forecast_curves(mtype, lag, fold, ax=None, title=None):
    """Plotea y_true vs yhat en train, val y test para un fold dado.
    Usa el horizonte h=1 (primera columna) para mantener la serie 1-D.
    """
    r = results_all[mtype][lag][fold]

    y_tr  = r['y_train_raw'][:, 0]
    y_val = r['y_val_raw'][:, 0]
    y_te  = r['y_test_raw'][:, 0]
    p_tr  = r['yhat_train'][:, 0]
    p_val = r['yhat_val'][:, 0]
    p_te  = r['yhat_test'][:, 0]

    n_tr  = len(y_tr)
    n_val = len(y_val)
    n_te  = len(y_te)

    # Ejes x contiguos
    x_tr  = np.arange(n_tr)
    x_val = np.arange(n_tr, n_tr + n_val)
    x_te  = np.arange(n_tr + n_val, n_tr + n_val + n_te)

    if ax is None:
        fig, ax = plt.subplots(figsize=(12, 3.5))

    # Bandas de fondo
    ax.axvspan(x_tr[0],  x_tr[-1],  alpha=0.05, color=C['blue'],   label='_nolegend_')
    ax.axvspan(x_val[0], x_val[-1], alpha=0.08, color=C['amber'],  label='_nolegend_')
    ax.axvspan(x_te[0],  x_te[-1],  alpha=0.08, color=C['coral'],  label='_nolegend_')

    # Series reales
    ax.plot(x_tr,  y_tr,  color=C['navy'], linewidth=0.8, alpha=0.6)
    ax.plot(x_val, y_val, color=C['navy'], linewidth=0.8, alpha=0.6)
    ax.plot(x_te,  y_te,  color=C['navy'], linewidth=0.8, alpha=0.6, label='Real')

    # Predicciones
    ax.plot(x_tr,  p_tr,  color=C['blue'],  linewidth=1.2, linestyle='--', alpha=0.8, label='Pred train')
    ax.plot(x_val, p_val, color=C['amber'], linewidth=1.2, linestyle='--', alpha=0.9, label='Pred val')
    ax.plot(x_te,  p_te,  color=C['coral'], linewidth=1.4, linestyle='--', label='Pred test')

    # Separadores verticales
    ax.axvline(x_val[0], color='gray', linewidth=0.8, linestyle=':')
    ax.axvline(x_te[0],  color='gray', linewidth=0.8, linestyle=':')

    # Anotaciones
    ax.text(x_tr.mean(),  ax.get_ylim()[1]*0.95, 'TRAIN', ha='center', fontsize=7, color=C['blue'],  alpha=0.7)
    ax.text(x_val.mean(), ax.get_ylim()[1]*0.95, 'VAL',   ha='center', fontsize=7, color=C['amber'], alpha=0.8)
    ax.text(x_te.mean(),  ax.get_ylim()[1]*0.95, 'TEST',  ha='center', fontsize=7, color=C['coral'])

    rmse = results_all[mtype][lag][fold]['rmse_test']
    ax.set_title(title or f'{mtype} | lag={lag}d | fold={fold} | RMSE_test={rmse:.4f}', fontsize=10)
    ax.set_xlabel('Muestra (h=1)')
    ax.set_ylabel('RV_15m')
    ax.yaxis.set_major_formatter(mticker.FuncFormatter(lambda x, _: f'{x:.2f}'))
    ax.legend(loc='upper left', ncol=3, fontsize=7)

# ── Función: identificar mejor, peor y mediano por (mtype, lag) ──────────────
def get_fold_ranking(mtype, lag):
    """Devuelve dict con fold mejor, peor y mediano según rmse_test."""
    rmse_by_fold = {
        f: results_all[mtype][lag][f]['rmse_test']
        for f in FOLDS
    }
    sorted_folds = sorted(rmse_by_fold, key=rmse_by_fold.get)
    n = len(sorted_folds)
    return {
        'best':   sorted_folds[0],
        'median': sorted_folds[n // 2],
        'worst':  sorted_folds[-1],
        'rmse':   rmse_by_fold,
    }

7. Conclusiones#

El objetivo de este trabajo fue construir un sistema de forecasting de volatilidad realizada para Bitcoin con horizonte de 7 días, evaluando tres arquitecturas de redes neuronales (MLP, RNN, LSTM) sobre datos diarios del período 2018–2025.

Sobre el problema#

Predecir volatilidad en mercados de criptomonedas es inherentemente difícil. BTC ha atravesado al menos cuatro regímenes distintos en el período estudiado: el crash de 2018, la consolidación de 2019–2020, el ciclo alcista de 2021 y el colapso de 2022. Cualquier modelo que generalice bien sobre esa heterogeneidad ya es un resultado no trivial.

Sobre los modelos#

Los tres modelos convergen al mismo rango de RMSE en el lag óptimo (14–21 días), con diferencias menores al 5% entre arquitecturas. Esto sugiere que el factor limitante no es la capacidad del modelo sino la predictibilidad intrínseca de la serie — la volatilidad de BTC tiene un componente estructural de ruido que ninguna arquitectura puede eliminar.

El MAPE en el rango 41–45% no es un fracaso del modelo: es una consecuencia directa de que la serie tiene observaciones cercanas a cero donde cualquier error absoluto pequeño produce un error relativo enorme. El RMSE y el MAE son las métricas relevantes aquí.

El test BDS confirma que los residuos no contienen estructura no lineal explotable, lo que indica que los modelos capturaron la mayor parte de la dependencia sistemática disponible en los datos.

Sobre la selección del lag#

El lag óptimo resultó ser 14–21 días. Lag=7 pierde contexto de ciclos semanales de volatilidad; lag=28 introduce regímenes heterogéneos que el modelo no puede reconciliar en un solo fold. El incremento de RMSE en lag=28 es consistente entre los tres modelos, lo que descarta causas arquitectónicas y apunta directamente al horizonte de memoria como variable de diseño crítica.

Sobre el sobreajuste#

El criterio de selección del grid search (gap_ratio < 0.15) garantizó que las configuraciones con sobreajuste quedaran fuera de la selección final. Los gap elevados observados en lag=28 no son un problema del modelo desplegado — son una señal correcta de que ese lag no debería usarse, y de hecho no se usa.

Sobre el deployment#

El modelo seleccionado (LSTM, lag=21) fue validado estadísticamente contra un baseline de persistencia mediante el test de Diebold-Mariano. Un p-value < 0.05 con RMSE inferior al baseline confirma que las predicciones aportan valor informacional real más allá de simplemente repetir el último valor observado.

La API expuesta vía FastAPI incluye monitoreo de drift en tiempo real: si la distribución de los inputs de producción se aleja del rango [p1, p99] del training, el endpoint /health lo refleja antes de que las predicciones se degraden silenciosamente.

Reflexión final#

Un modelo de forecasting financiero no se evalúa solo por su RMSE. Se evalúa por si captura la dinámica del fenómeno, si generaliza entre períodos, si supera estadísticamente a alternativas triviales y si puede mantenerse en producción de forma monitoreable. Este trabajo cumple las cuatro condiciones y el objetivo más allá de lo académico, es poder integrar su arquitectura en un sistema real funcional.
